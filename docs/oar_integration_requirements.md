# OAR 智能体运行时集成与会话模式演进需求

> 本文档记录关于在本项目中集成 Open Agent Runtime (OAR)、会话模式划分、官方套餐直连及架构演进的原始需求。
> 按照要求严格保留原始需求描述，不做过度衍生加工。

---

## 一、 原始需求清单 (Raw Requirements)

### 需求 1：引入 OAR 引擎作为可选方案，划分三种会话模式
* **原始提问/需求**：
  > “探讨一个问题，可以把 oar 集成到项目中，代替对话模式的调用 tmux 吗？”  
  > “可以帮我实现一个版本看看，作为可选的引擎，这样新建智能体会话就有几种模式 纯会话 会话与终端 终端 这三者，”
* **核心内容**：
  1. 将 `@botiverse/oar` 集成到系统中，作为智能体运行的可选引擎。
  2. 新建智能体会话时支持三种模式选择：
     - **纯会话 (Chat Only)**：基于 OAR 运行时驱动，无终端黑盒按键盲发与错位干扰。
     - **会话与终端 (Chat & Terminal / 双模)**：保留现有的 Tmux 混合模式，支持对话且随时切回终端。
     - **纯终端 (Terminal Only)**：直接使用 Tmux 命令行终端。

---

### 需求 2：纯会话工具调用与工作区真实落地（去脏标签）
* **原始提问/需求**：
  > “当前 oar 会话，每次都会先打印返回 先确认一下工具是否恢复，然后直接在工作区落地。  
  > `<｜｜DSML｜｜ calls> <｜｜DSML｜｜ invoke name="bash"> <｜｜DSML｜｜ parameter name="command" string="true">pwd; echo "---"; ls -la</｜｜DSML｜｜ parameter> <｜｜DSML｜｜ parameter name="description" string="true">确认当前工作区目录</｜｜DSML｜｜ parameter> </｜｜DSML｜｜ invoke> </｜｜DSML｜｜ calls>`”
* **核心内容**：
  1. 消除每次对话前模型输出的“先确认一下工具是否恢复”等多余提示语。
  2. 模型生成的工具调用（如 DSML / bash 命令 / 文件查看），必须直接在当前工作区真实落地执行。
  3. 执行结果需回传给模型形成 ReAct 闭环，并将最终人类可读结果呈现给用户，不在前端展示裸露的 DSML 标签。

---

### 需求 3：确保使用 Antigravity (agy) 等官方原生套餐与模型配额
* **原始提问/需求**：
  > “难道这里 agy 用的不是 agy 的套餐吗”
* **核心内容**：
  1. 会话选择 Antigravity (`agy`) 时，必须 100% 使用用户本机的官方 agy 账号套餐与 Google 官方 Gemini 模型配额，不能走本地网关或第三方中继模型。
  2. Claude 会话同理优先走官方 `claude` CLI 的登录认证与套餐配额。

---

### 需求 4：规范扩展 OAR 功能，而非脱离 OAR 单独实现
* **原始提问/需求**：
  > “那这是不是扩展 oar 的功能还是你跳出 oar 实现了”
* **核心内容**：
  1. 不应脱离 OAR SDK 单独写胶水脚本或降级调用。
  2. 应遵循 OAR 架构规范，通过 `@botiverse/oar` 提供的扩展机制（如 `defineRuntime` / 自定义 Runtime Registry）将本机 CLI 适配器注册进 OAR 体系。
  3. 对外统一暴露标准 OAR Session 合约（`prompt`、`abort`、`eventsOf` 等），保持接口一致性。

---

### 需求 5：探索未来将现有的双模统一接入 OAR 架构
* **原始提问/需求**：
  > “可以这么实现，这种方式是不是可以未来把现在的双模接过来？”
* **核心内容**：
  1. 规划未来将“会话与终端（双模）”也接入 OAR 体系。
  2. 底层可由 tmux 保证终端 PTY 的常驻与终端交互，上层由 OAR 提供统一的结构化会话状态与事件流。
